Attention's mixing step reads no weights. The projections on either side have weight tables like any others, while the kernel that scores past keys and blends past values reads only the conversation's KV cache. For one person's token in a full layer, that is every key and value the conversation has stored on this GPU: {bytes(full)} at {count(CONTEXT_TOKENS)} tokens, in each of the {LAYERS.full} full layers of every pass.

## What the kernel reads

On each GPU, {Q_HEADS} query heads share {KV_HEADS} key-value heads ({KV_GROUP} query heads per KV head under <Term id="gqa">grouped-query attention</Term>). That sharing makes the cache {KV_GROUP} times smaller than giving each query head its own keys and values.

Each number in the cache is stored in <Term id="fp8">FP8</Term> (1 byte). One token's entry in one layer on one GPU is {KV_HEADS} KV heads × (1 key + 1 value) × {HEAD_DIM} numbers × 1 byte = {entry} bytes. Across {count(CONTEXT_TOKENS)} tokens, a full layer reads {bytes(full)} of cache.

Those entries do not sit in one contiguous block of HBM. Because conversations grow unpredictably and finish at different times, reserving one large contiguous buffer per user would waste memory. Serving engines instead use <Term id="pagedAttention">PagedAttention</Term>, borrowing the idea of virtual-memory paging: they place fixed-size cache pages wherever HBM has room and track each conversation's pages in a <Term id="page">page table</Term>. A real attention kernel reads that page table first to locate each token's keys and values.

## Too little work to go around

Because {KV_GROUP} query heads share each KV head, launching {Q_HEADS} separate programs (one per query head) would let {KV_GROUP} independent programs stream the same keys and values from memory, risking up to {KV_GROUP}× redundant HBM traffic whenever active caches outgrow L2. Real GQA decode kernels therefore give one program all {KV_GROUP} query heads of a KV head, loading each K/V tile from HBM once and reusing it across all {KV_GROUP} queries.

That avoids redundant reads, yet leaves a different problem: on this GPU there are only {KV_HEADS} KV heads. Launching one program per KV head creates just {unsplit.programs} programs for {H200.sms} compute blocks, leaving {unsplit.idle} blocks idle and starving HBM of in-flight requests.

The fix applies <Term id="splitK">split-K</Term> to the conversation length: cut each KV head's {count(CONTEXT_TOKENS)}-token history into {GQA_SPLITS} slices and give every slice its own program. Now {KV_HEADS} KV heads × {GQA_SPLITS} slices make {count(split.programs)} programs across {H200.sms} compute blocks. Each program reads {count(split.sliceTokens)} tokens ({bytes(split.bytesPerProgram)}) once for all {KV_GROUP} query heads, keeping the KV cache payload at {bytes(split.totalBytes)} (with small extra traffic for queries and partial slice merges) while putting nearly every block to work.

The price of splitting is a small second kernel that merges each head's {GQA_SPLITS} partial results into one output. PyTorch's <a href="https://pytorch.org/blog/flash-decoding/">Flash-Decoding post</a> measures what splitting gains on long single-user contexts. At ideal bandwidth, streaming the full layer's {bytes(full)} takes {us(memoryUs(full))}; a sliding layer reads only the latest {count(SLIDING_WINDOW)} tokens ({bytes(window)}, an ideal of {us(memoryUs(window))}), where fixed kernel overhead outweighs the cache read.

## Putting slices back together

Early attention implementations computed all scores into global memory, ran a separate softmax kernel over them, and read those weights back to blend the values. <Term id="flashAttention">FlashAttention</Term> eliminated those round-trips through IO-aware tiling and fusion, building on <Term id="onlineSoftmax">online softmax</Term> (introduced by Milakov and Gimelshein in 2018): scanning keys and values one tile at a time in on-chip registers and rescaling the running softmax total whenever a higher score appears. The same algebra lets us split a conversation across {GQA_SPLITS} programs and recombine their partial results cleanly.

<Predict question="Each slice blends the values of its own tokens. Can the second kernel simply average all the slices' blends together?">
	<p>
		No. A token's share is its <code>e^score</code> divided by the total across the whole conversation, and no slice knows that global total. A plain average would give a slice full of irrelevant tokens the same weight as the slice holding the one word that matters.
	</p>
</Predict>

Instead, each slice reports its running total alongside its blend so the second kernel can weigh every slice proportionally.

One detail keeps the exponentials safe: `e^score` overflows 32-bit floats for scores above about 88.7. Kernels therefore subtract the largest score seen so far and compute `e^(score − largest)`, which stays between 0 and 1, while keeping track of `largest`. Below are four scores computed all at once, then split into two slices and recombined.

<Figure surface="paper" label="softmax in two slices, recombined">
	<SplitSoftmax />
</Figure>

Slice 2 counted its total against its own peak score ({worked(s2.max)}), whereas slice 1 peaked higher ({worked(w.top)}). Because `e^(score − 2) × e^(2 − 3) = e^(score − 3)`, the second kernel rescales slice 2's total onto their shared maximum by multiplying by <code>e^({worked(s2.max)} − {worked(w.top)}) = {worked(s2.shrink)}</code>. It then multiplies each slice's blend by its adjusted total, sums those weighted blends, and divides by the sum of adjusted totals to recover the unsplit answer. Splitting a context across compute blocks and recombining partial softmaxes this way is <Term id="splitContext">split attention</Term> (often called Flash-Decoding).

The same rescaling happens inside each slice: as a program loops tile by tile, whenever a later tile holds a larger score than earlier tiles, it multiplies its saved running total and weighted sum by `e^(old_max − new_max)` before adding the new tile.

## The slice kernel

To keep the indexing transparent, the teaching kernel below uses the simpler per-query-head layout (one program per query head and slice) rather than grouping all {KV_GROUP} query heads per KV head as described above. A production kernel for Muse Spark Open adds four layers on top: grouping all {KV_GROUP} query heads per KV head so HBM is read once, looking up entries through the page table, applying FP8 dequantization scales, and fusing surrounding norm and gate steps.

Count the memory trips first: each program loads its query once, walks its slice's keys and values one tile at a time (each once), and stores its slice's blend along with its largest score and running total.
