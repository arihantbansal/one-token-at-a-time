To the GPU, a pass is a chain of over {count(Math.floor(perPass / 100) * 100)} kernels in a row. For one person on one GPU, a single layer runs about {chain.length} kernels in sequence, repeated {LAYERS.total} times per token, with each kernel finishing before the next reads its output.

The chain is longer than a layer's high-level diagram because several stages split into multiple kernels: the experts alone take {expertKernels} kernels (sorting tokens by expert, multiplying, combining outputs), and the small ops around attention each run on their own in stock code. The full order sits in the [interactive layer map](/challenge#layer-map).

The big kernels read megabytes of weights, so bandwidth sets their ideal time. Between them sit {small} small kernels touching a few kilobytes of working numbers: normalizing, gating, picking experts, and updating the running total.

Production serving sees the same tax. Profiling <Term id="sglang">SGLang</Term> on an H200, the challenge's organizers found the small steps between big kernels take roughly a quarter of a single-user decode pass, as the <a href={officialUrl("muse_decode_layer")}>whole-layer problem</a> describes.

## Who waits for whom

Normally the CPU queues kernels asynchronously without waiting for the previous one to finish. While the GPU runs a big projection, the CPU easily stays ahead and queues several more kernels behind it. When tiny kernels arrive in a row, the GPU finishes each one faster than the CPU can submit the next and sits idle. Below are the three cases on a shared timeline: big kernels, small kernels queued one by one, and small kernels replayed together.

<Figure surface="paper" label="the CPU queues, the GPU runs">
	<LaunchQueue />
</Figure>

Big kernels keep the GPU fed; small ones leave it waiting on the CPU. Servers fix CPU starvation by recording a pass's kernel chain once and replaying it with a single CPU call, a <Term id="cudaGraph">CUDA graph</Term>. Because the CPU does not run Python between kernels during replay, the graph's kernels and shapes are fixed at capture time (tensor contents can update in place). Servers therefore capture one graph per batch size, and a kernel that inserts a Python `if` branch on runtime tensor values breaks graph capture.

A graph trims CPU launch cost to near zero, yet each kernel in the graph still starts on the compute blocks, fetches its first data, and finishes before the next starts. The only way to remove that per-kernel cost is to launch fewer kernels.

## Three steps in one kernel

After attention, Muse Spark Open normalizes each head's output to a standard size and multiplies it by a gate, a companion list made by the same projection as the query and squashed through a sigmoid into 0 to 1. Written as separate PyTorch ops, that sequence takes three kernels: normalize, squash the gate, and multiply.

<Figure surface="paper" label="the gated norm, three kernels or one">
	<FuseTrips />
</Figure>

The three-kernel version writes two intermediate lists out to global memory and reads them back, {trips(NORM_GATE_UNFUSED)} global-memory trips and {NORM_GATE_UNFUSED.length} launches. One combined kernel keeps those intermediates in registers: {trips(NORM_GATE_FUSED)} trips and one launch. Combining adjacent operations into one kernel is <Term id="fusion">fusion</Term>. For one token each list is only {bytes(NORM_GATE_LIST_BYTES)}, small enough to sit in L2 cache rather than crossing HBM, so the immediate saving is cutting two launches and their global-memory instructions; at larger batches the intermediate tensors outgrow L2 and fusion saves HBM traffic as well. Triton's <a href="https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html">fused softmax tutorial</a> makes the same count on wider rows and measures the speedup.

## Eight GPUs as one

Each pass runs across all {GPUS} H200s together, splitting every layer two ways:

1. <Term id="tensorParallel">Tensor parallelism</Term> for attention: the model's {allHeads} query heads divide evenly so each GPU computes {Q_HEADS} of them. Because each of the {count(HIDDEN)} outputs leaving attention is a weighted sum over all {allHeads} heads, each GPU's output projection sums only its own {Q_HEADS} heads, producing a partial subtotal. The {GPUS} GPUs exchange and add those eight subtotals so every card holds the full sum, an <Term id="allReduce">all-reduce</Term>.
2. <Term id="expertParallel">Expert parallelism</Term> for the experts: each GPU holds {LOCAL_EXPERTS} of every layer's {N_EXPERTS} experts and runs whichever of its local experts were chosen, producing a partial weighted blend of the token's {TOP_K} experts. A second all-reduce adds the eight cards' pieces together.

In this draw, {idleGpus === 3 ? "three" : count(idleGpus)} GPUs had nothing to read and waited for the busiest card. Each expert takes {us(memoryUs(EXPERT_BYTES))} to read at peak bandwidth, so an uneven routing draw stretches the pass.

Even when the exchanged vector is tiny ({bytes(HIDDEN * 2)} for one token), collectives add up over {LAYERS.total} layers: {allReducesPerPass} cross-GPU all-reduces per pass, plus {LAYERS.total} small all-gathers at tiny batches ({SLICED_MAX_TOKENS} tokens or fewer), where each GPU computes a 1/{GPUS} slice of the final expert projection and shares its slice so every card holds the full vector. At typical NVSwitch collective latencies of several microseconds each, communication adds on the order of a millisecond to a real {GPUS}-GPU pass, substantial next to our {us(passUs)} single-GPU ideal.
