Every token of a prompt is known before the first pass starts, so all of them can share one read of the weights the way 32 people's tokens do. A reply cannot, because each token feeds the pass that chooses the next. Reading the prompt together is <Term id="prefill">prefill</Term>, and on this server long prompts are cut into chunks of {count(chunk)} tokens using <Term id="chunkedPrefill">chunked prefill</Term> so they can interleave cleanly with active replies.

You can feel the difference from outside. Send a long message to a chatbot and there is a pause before the first word appears, then words stream steadily. That pause is <Term id="ttft">time to first token</Term> (TTFT), mostly spent reading your prompt. It is also the hardware reason AI APIs usually price output tokens several times higher than input tokens: prices reflect business choices too, yet the gap between reading in parallel and writing one token at a time is the underlying mechanism.

A busy server may also queue your message, read it in chunks between other people's decode passes, and spend milliseconds sending the first token back across the network.

## Each token sees only its past

Although prefill reads prompt tokens together, each may attend only to itself and the tokens before it: token 500 sees the 499 before it and not token 501. The model was trained to predict each token strictly from its past, so obeying the same mask during prefill gives identical activations whether tokens are read together or written one by one. Drawn as a grid of which token sees which, that rule forms a triangle.

Eight tokens fill {looks(8)} squares; doubling to 16 fills {looks(16)}, nearly four times as many. In full-attention layers, attention's work grows quadratically with prompt length when reading a prompt from scratch.

At real sizes, a {count(chunk)}-token chunk at the start of a conversation (`ctx 0`) takes at least {us(firstChunk)} in a full-attention layer. The same chunk arriving {count(65536)} tokens into a session takes at least {us(lateChunk)}, because each new token also attends over all {count(65536)} earlier entries. Sliding-window layers do not grow this way, since each token looks back at most {count(SLIDING_WINDOW)} tokens.

## Keeping the cache between turns

In a long conversation, why doesn't each new message re-prefill all {count(CONTEXT_TOKENS)} earlier tokens? The server keeps the conversation's cache in HBM after a reply finishes. When the next turn arrives, prefill skips the existing history and pushes only the {count(TURN_TOKENS)} new tokens through the weight tables, about {count(CONTEXT_TOKENS / TURN_TOKENS)} times fewer tokens through the projections (though those new tokens still attend back over the kept cache, and every later decode pass still reads it). Reusing past cache entries across turns is <Term id="promptCaching">prompt caching</Term>, which is why cached input tokens are cheaper to buy.

It works across conversations too. Requests that start with identical text (such as a shared system prompt or tool definitions) produce identical cache entries for that prefix, so the server stores one shared copy. SGLang tracks reusable prefixes in a prefix tree called <Term id="radixAttention">RadixAttention</Term>. Shared prefixes are the one place two conversations ever share anything besides model weights.

Kept caches take HBM whether users are actively streaming or idle, and raw remaining memory on each GPU holds at most about {count(conversationsBothCaches)} conversations of {count(CONTEXT_TOKENS)} tokens before buffers and non-layer weights. Servers therefore keep hot prefixes warm and evict stale ones when active batches need space.

## Can one pass write more than one token?

Batching pools tokens across users; prefill pools tokens across a prompt. To speed up a single user's reply stream, <Term id="speculative">speculative decoding</Term> uses a small, fast draft model to guess several tokens ahead, such as {DRAFT_TOKENS} tokens at once. Because all {DRAFT_TOKENS} tokens exist up front, the big model checks them together in one parallel verify pass, each position looking at the conversation plus earlier guesses. (In practice, a verify pass of {DRAFT_TOKENS} positions typically bundles the last accepted token with {DRAFT_TOKENS - 1} guesses so the big model can score every guess and still emit one bonus token if all {DRAFT_TOKENS - 1} match.)

The big model accepts guesses up to the first disagreement, and because each position in a causal pass already predicts the next token, the last matching position yields the big model's own replacement token without a second pass. Guesses after the first mismatch are discarded. (The diagram shows greedy verification; when a server samples randomly, a lossless rejection-sampling rule keeps the big model's output distribution unchanged.)

Three right guesses gave four tokens from one pass; a wrong first guess still gave one, the same as an ordinary decode pass. Checking an {DRAFT_TOKENS}-token verify pass costs about {draftCheckPasses.toFixed(1)}× the ideal time of a 1-token pass, mostly because {DRAFT_TOKENS} tokens activate more experts than one does. Add the draft model's own time, and speculative decoding pays off whenever acceptance rates clear that overhead. Hugging Face's [post on assisted generation](https://huggingface.co/blog/assisted-generation) animates the loop and measures real speedups.

A server can spend its idle arithmetic on more people in each pass, on prompts, or on drafts. How much of the opening's {count(Math.round(ARITHMETIC_TOKENS_PER_SECOND / 1000) * 1000)} tokens a second does all of that win back?
