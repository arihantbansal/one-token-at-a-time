Because every user on a server runs the same model weights, a second person's token can ride through a dense projection without reading an extra weight from HBM. At peak bandwidth, each 16-bit weight arriving on chip leaves time for about {perWeight} tensor-core operations, and a single token uses 2. Running another user's token against that same weight adds almost only arithmetic. Experts are the exception, because a second token may choose experts the first one did not.

Weight reads stay at {toyWeights} whether the pass carries 1, 4, or 16 tokens, while multiplications grow from {toyWeights} to {count(toyWeights * 4)} to {count(toyWeights * 16)}. The shape of the work changes too: one token multiplies a matrix by a vector (<Term id="gemv">GEMV</Term>), whereas several tokens multiply a matrix by a matrix (<Term id="gemm">GEMM</Term>), the 2D tile shape <Term id="tensorCore">tensor cores</Term> were built for. Tokens traveling through the model together form a <Term id="batch">batch</Term>, which is how a server puts idle arithmetic to work.

## When arithmetic catches up

Each extra token in a batch adds two operations per weight (1 operation per byte for 16-bit weights), climbing along the <Term id="roofline">roofline</Term> toward the chip's balance point. How far can a batch grow before arithmetic overtakes bandwidth?

<Predict question="A server batches 16 people's tokens through the layer's largest projection (`pooler`) in one pass. Compared with one person, how much more data does it read, and how much more arithmetic does it do? On tensor cores, is the chip still waiting on memory?">
	<p>Weight reads stay at {bytes(weightBytes(pooler, 16))}, with only a small slice added for 16 tokens' activations, while arithmetic grows 16×.</p>
	<p>On tensor cores, the chip is still memory-bound: 16 operations per byte sits far short of the {balance}-op/byte tensor-core ridge, so 16 people cost barely more ideal time than 1. On scalar FP32 CUDA cores, by contrast, 16 tokens already pass the {fp32Balance}-op/byte ridge.</p>

On tensor cores, moving data barely grows while arithmetic climbs linearly, crossing the weight-only balance point at ~{balance} tokens (and ~{poolerRidge} tokens once `pooler`'s input and output activations are included). A 32-person decode batch stays well below that ridge, so inside dense projections 32 people take little more ideal time than one.

## Faster in total, slower for each

If dense projections barely slow down from 1 person to 32, batching sounds nearly free. Yet look at ideal pass speeds across the whole model: solo, one person gets about {count(solo.each)} tokens a second; at 32 people, the server produces about {count(many.total)} tokens a second in total ({times(many.total / solo.total, 0)} as many), while each individual drops to about {count(many.each)}, roughly {percent(many.each / solo.each)} of solo speed. If shared weights barely grew, what slowed each person down?

## Caches never share

Every active user carries a private KV cache (except for identical prompt prefixes, covered in Chapter 9). In every full-attention layer, attention reads every entry of every cache in the pass.

<Figure surface="paper" label="one cache per person">
	<Fragment slot="caption"><Key as="bytes">Cache read by one full layer</Key> on one GPU in one pass, with lengths spread between {count(shortest)} and {count(longest)} tokens to match the contest's batches.</Fragment>
	<KvPeople />
</Figure>

Cache bytes add up person by person. At 32 people, one full layer reads {bytes(fullCache32)} of cache, more than {Math.floor(fullCache32 / layerWeights32)} times its {bytes(layerWeights32)} of shared projection weights. Sliding-window layers read only each person's latest {count(SLIDING_WINDOW)} tokens, so almost all of the cache bill comes from the {LAYERS.full} full-attention layers.

## More people, more experts

Expert weights are shared whenever two tokens in a batch choose the same expert. Still, 32 tokens touch many more of each GPU's {LOCAL_EXPERTS} local experts than 1 token does.

## Room in memory and continuous batching

Bandwidth is one limit; HBM capacity and scheduling are another. Each H200 holds {H200.memoryGB} GB, of which layer weights take about {count(weightBytesPerGpu / 1e9)} GB. One {count(CONTEXT_TOKENS)}-token conversation needs {bytes(fullLayerCacheBytes(CONTEXT_TOKENS))} per GPU for its full-attention caches plus {bytes(slidingCachePerConv)} for sliding windows ({bytes(perConvCacheBytes)} in total), so raw remaining HBM could hold about {count(conversationsBothCaches)} such conversations before non-layer weights and buffers (or about {count(conversationsThatFit(CONTEXT_TOKENS))} counting full layers alone).

Thirty-two active conversations use only about {bytes(activeCache32)} of KV cache per GPU, well under that memory ceiling. In production serving, active concurrency is typically kept far below raw memory capacity both to keep per-user streaming responsive and to leave tens of gigabytes free for idle prompt caches between turns (Chapter 9), activation space, and CUDA-graph buffers.

When traffic fills the available slots, newcomers have to wait. Picture one GPU's memory as sixteen toy blocks and see what happens when another user arrives.

<Figure surface="paper" label="waiting for room">
	<MemoryRoom />
</Figure>

Dara waited even with spare arithmetic on the chip because her cache had no room, and every active user's cache grows by one entry per pass, so a server must leave headroom or pause conversations when memory runs tight.

This is why serving engines like <Term id="sglang">SGLang</Term> and vLLM go far beyond Hugging Face Transformers' default `model.generate()` loop: they combine paged KV memory, captured CUDA graphs, and <Term id="continuousBatching">continuous batching</Term>. Rather than holding newcomers until an entire batch finishes, continuous batching lets finished replies leave and waiting requests join on the very next pass. Anyscale's [post on continuous batching](https://www.anyscale.com/blog/continuous-batching-llm-inference) traces the schedule pass by pass and measures its throughput gains.

A newcomer's first pass is different: it arrives with an entire prompt of hundreds or thousands of tokens. Running that prompt straight through would stall everyone mid-reply, so servers slice long prompts with <Term id="chunkedPrefill">chunked prefill</Term> and weave chunks between decode passes.
