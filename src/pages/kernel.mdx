Every single-user pass pulls {count(passBytesPerGpu() / 1e9)} GB from HBM into the busiest GPU's registers, and code running on the compute blocks asks for every byte. A GPU runs that code as a <Term id="kernel">kernel</Term>: many copies of one function at once, each on its own piece of the work. When a new model combines pieces that stock libraries were not tuned together for (such as 4-bit NVFP4 experts, custom attention gating, and hybrid FP8 attention), generic kernels can land several times above the hardware floor, which is why kernel engineers and coding agents edit them directly.

The kernels here are written in <Term id="triton">Triton</Term>, a Python-like language where you write what one copy does to an entire block of data while the compiler handles thread layout and how threads load memory (rather than hand-scheduling individual threads in CUDA). Its <a href="https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html">vector-add tutorial</a> is about the shortest complete kernel there is.

## One program per output

Take the twelve-weight projection: a matrix-vector multiply (<Term id="gemv">GEMV</Term>) producing three outputs, each a weighted sum of the token's four numbers with its own row of four weights. Because no output depends on another, three copies of the function can compute them at once if each knows which row it owns.

<Figure surface="paper" label="the twelve-weight projection as three programs">
	<TiledProjection show={["programs"]} />
</Figure>

Each running copy of a Triton kernel is a <Term id="program">program</Term>. Program 2 computes output 2: it loads row 2 of the weights and all four of the token's numbers, and writes {worked(p2.y)}. The only difference between the three programs is the number each is given.

A program is not a thread. Triton runs each program on one compute block as a group of threads ({TRITON_WARPS} warps by default, closest to a thread block in CUDA), and one block can hold several programs at once. Programs start whenever a block has room and finish in no fixed order, so none may assume another has finished.

## Tiles, a loop, and a mask

The real projections have the same shape at larger sizes. Below are the five dense projections on one GPU, drawn to scale with width for inputs and height for outputs. Each GPU owns {Q_HEADS} query heads and {KV_HEADS} key-value heads of {HEAD_DIM} numbers each. That gives `out of attention` {count(attnOut.cols)} inputs ({Q_HEADS} × {HEAD_DIM}), while `into attention` packs {Q_HEADS} query heads, {Q_HEADS} companion gate heads that scale attention's output afterward, {KV_HEADS} key heads, and {KV_HEADS} value heads into {count(qkvGate.rows)} outputs.

The projection into the experts (`pooler`) has {count(pooler.rows)} rows of {count(pooler.cols)} weights. One program per row would spawn {count(pooler.rows)} tiny programs, so the kernel assigns each program a block of rows called a <Term id="tile">tile</Term>.

Tiles rarely divide a table evenly, and the last one overhangs the edge. To keep out-of-bounds slots from reading invalid memory, the kernel carries a boolean <Term id="mask">mask</Term> switching off places past the edge. On the 3-row toy, tiles of two rows make two programs, and the second tile has only one real row, leaving one slot hanging past the edge.

The real-size kernel also adds a loop along the columns, because {PROJ_BLOCK_N} full rows of {count(pooler.cols)} weights will not fit in registers at once. Each program walks {PROJ_BLOCK_K} columns at a time ({grid.steps} steps), keeping each row's running sum in <Term id="fp32">FP32</Term> so adding thousands of products does not drift from 16-bit rounding. ## Neighbors in memory

Why walk along a row rather than down a column? Weight tables sit in memory row after row, so neighboring weights in a row have neighboring addresses. GPU memory hands data over in {MEMORY_SECTOR_BYTES}-byte sectors. When the {H200.warpSize} threads of a warp request neighboring addresses, their requests merge into a few whole sectors; when they stride down a column far apart, each thread costs its own sector.

<Figure surface="paper" label="one warp's reads, together and scattered">
	<Coalesce />
</Figure>

Reading down a column asks for {scattered} times as many sectors for the same {H200.warpSize} weights. Some of those sectors may already sit in the L2 cache, yet scattered reads still waste the bandwidth that sets the time. Combining neighboring reads into wide transactions is <Term id="coalescing">coalescing</Term>, and Triton arranges threads to get it whenever the tile's inner dimension walks contiguously along memory.

## What sets its time

Kernel 1 reads each weight once and performs two operations on it (1 operation per byte), far below both the tensor-core ridge (~{balance}) and the FP32 CUDA-core ridge (~{fp32Balance}). Computing `tl.sum(w * x)` on scalar CUDA cores therefore does not hold single-token decode back. Its ideal time is bytes over bandwidth: {us(floorUs(projectionCost(pooler, 1)))} for `pooler`, {us(layerUs)} for all five projections in one layer, or {us(layerUs * LAYERS.total)} across {LAYERS.total} layers.

A real kernel falls short of that floor when too few programs keep too few requests in flight to saturate HBM, when uncoalesced reads waste memory sectors, or when a program waits for one tile to finish multiplying before requesting the next (rather than prefetching the next tile while multiplying the current one, called software pipelining).

## An edit that changes only the time

Suppose an agent edits one number in Kernel 1's launch, the tile height `BLOCK_N`, leaving the body untouched.

<Figure label="the same kernel, four tile heights">
	<TileEdit />
</Figure>

Every tile height produces the same outputs, because each row is summed in the same order. What changes is how the grid maps onto the chip (the drawing illustrates an even spread across blocks; actual concurrent residency also depends on registers, shared memory, and hardware scheduling):
- At <code>BLOCK_N = {PROJ_BLOCK_N}</code>, `pooler` launches {count(grid.programs)} programs on {H200.sms} compute blocks, leaving {count(grid.idle)} blocks idle and putting at most one program ({TRITON_WARPS} warps) on each active block.
- Halving `BLOCK_N` to {PROJ_BLOCK_N / 2} launches {count(halfTiles)} programs, covering all {H200.sms} blocks and allowing up to two resident programs ({TRITON_WARPS * 2} warps) per block when registers permit, keeping more memory requests in flight.
- Shrinking `BLOCK_N` to 1 floods the grid with {count(pooler.rows)} tiny programs, issuing {count(pooler.rows)} logical loads of the token's {count(HIDDEN)}-number vector (most hitting cache, yet still paying instruction and scheduling overhead per row).

Short tables face an even tighter grid limit: `router` has only {count(router.rows)} rows, so at <code>BLOCK_N = {PROJ_BLOCK_N}</code> it launches just {routerGrid.programs} programs on {H200.sms} compute blocks. When splitting rows cannot fill the chip, kernels split along the columns (`K`) as well, a technique called <Term id="splitK">split-K</Term> that returns in Chapter 7.

Tile width (`BLOCK_K`), warps per program (`num_warps`), prefetch stages (`num_stages`), and tile order are choices of the same kind. None changes the mathematical specification (changing `BLOCK_K` reorders floating-point additions, so outputs are checked within a tolerance rather than bit for bit). That is what lets an agent optimize a kernel it could not derive from scratch: change a launch setting, check accuracy against a reference, time it, and keep the faster version.
