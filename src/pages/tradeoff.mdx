## What batching buys back

A server has two speeds that pull apart: total <Term id="throughput">throughput</Term> across everyone it serves, and the per-user streaming speed each person sees.

<Figure surface="paper" label="total against each">
	<Throughput />
</Figure>

The first step does most of the work in both directions. Going from 1 person to 16 multiplies total output by {count(mid.total / solo.total)}× while trimming each person to {percent(mid.each / solo.each)} of solo speed. Going on to 32 multiplies total throughput by another {times(many.total / mid.total, 1)} and costs each user {percent(1 - many.each / mid.each)} of their speed. By 16 people, shared projection weights are already well-amortized; each newcomer mainly adds a private cache and a few newly chosen experts.

Why does decode batching stop so far short of {about(arithmetic, 1000)} (or {about(longArithmetic, 1000)})? Reaching the tensor-core <Term id="roofline">roofline</Term> ridge requires about {count(BALANCE_POINT)} tokens sharing every 16-bit weight, or about {count(BALANCE_POINT * NVFP4_BYTES / 2)} sharing each NVFP4 expert weight (because {worked(NVFP4_BYTES * 8)}-bit weights are nearly four times smaller than 16-bit weights and arrive nearly four times faster). Only shared projections amortize one read across a whole batch. Caches belong to individual conversations, and experts serve only the tokens that chose them, so growing the batch raises the share of bytes that cannot be shared.

## Selling speed

Suppose an {GPUS}× H200 server costs the same per hour regardless of batch size. At 1 user it writes about {count(solo.total)} tokens a second; at 32 users it writes about {count(many.total)}. A token written for one person alone therefore takes about {count(many.total / solo.total)} times as much of the server's hour as a token written in a 32-user batch.

A service running smaller batches gives each user faster tokens while spreading its GPU bill over fewer of them. Raising the batch size makes tokens cheaper and slower per user. The same hardware can sell cheap background throughput or fast interactive replies, and batch size chooses between them.

## Ideal and measured

How close does real serving software get to these floors? Across the {count(loadFloors("muse_decode_layer").length)} loads of `muse_decode_layer`, combined with the judge's geometric mean, the ideal pass floor is {microseconds(layer.ideal)}. <Term id="sglang">SGLang</Term>'s baseline kernels took {microseconds(layer.sglang)}, about {times(layer.sglang / layer.ideal, 1)} the ideal{layer.best !== undefined && <>, while the fastest entry took {microseconds(layer.best)}, {times(layer.speedup, 1)} faster than SGLang and still {times(layer.best / layer.ideal, 1)} the ideal floor</>}.

That gap is everything the ideal cost model leaves out:
- Imperfect bandwidth and cache reuse: real kernels rarely hit 100% of rated HBM bandwidth and sometimes read data more than once.
- Per-kernel launch and drain overhead: starting and finishing {kernelsPerLayer} kernels per layer ({count(kernelsPerLayer * LAYERS.total)} per pass) adds fixed tax whenever small ops are not fused.
- Imperfect overlap: overlapping HBM transfers and arithmetic across uneven context lengths and skewed MoE groups is difficult.
- Cross-GPU communication: outside single-GPU kernel benchmarks, an {GPUS}-GPU server also pays for {2 * LAYERS.total} NVLink <Term id="allReduce">all-reduces</Term> per pass (plus {LAYERS.total} small all-gathers at tiny batches of {SLICED_MAX_TOKENS} tokens or fewer).

That room between stock serving software and the silicon floor is where kernel engineers and coding agents work. Every microsecond saved becomes either faster replies per person or more users on the same hardware.

## Pocket equations

Whenever a model's active weights stream from main memory on every token, three back-of-the-envelope formulas estimate decode ceilings and bottlenecks for any model and GPU (for deeper derivations, see Google's [JAX Scaling Book: Inference](https://jax-ml.github.io/scaling-book/inference/) and Horace He's [Making Deep Learning Go Brrrr](https://horace.io/brrr_intro.html)):

- Single-user decode ceiling: `tokens/s ≈ memory bandwidth ÷ (active weight bytes + KV cache bytes read per token)`
- Hardware ridge (critical batch size, weights only): `batch ≈ (GPU FLOP/s ÷ HBM bytes/s) × (bytes per weight ÷ 2)`, about {count(BALANCE_POINT)} tokens for BF16 weights on H200 tensor cores, {count(BALANCE_POINT * NVFP4_BYTES / 2)} for NVFP4, and {count(FP32_BALANCE_POINT)} for BF16 weights on FP32 CUDA cores.
- KV cache entry per cached token (one layer, one GPU): `2 × KV heads × head dim × bytes per number` ({kvEntryBytes} bytes here in FP8; multiply by the number of attended tokens in the conversation to get bytes read per generated token).

## Your own machine

That first equation works on any computer whose active weights stream from main memory, from an H200 node to the laptop on your desk. Writing one token at a time for yourself, every active weight reads once per token, so memory bandwidth divided by bytes read gives the physical ceiling.
