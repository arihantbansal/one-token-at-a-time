The <a href="https://openkernelchallenge.dev/">Open Kernel Challenge</a> asked how much faster Meta's Muse Spark Open could run on NVIDIA H200 GPUs. Organized by Paradigm with Meta and Andromeda, it published the system data this guide uses: the model's layer shapes, <Term id="sglang">SGLang</Term>'s baseline kernels, ideal floors, and measured timings. What follows describes the problems and scoring without prescribing solutions.

## Two tracks

The kernel track ({kernelTrack}, {contestYear}) posed five standalone problems, each a slice of one layer as one GPU of an {GPUS}-GPU server runs it. An entry was a single Python file. The judge checked its outputs against a high-precision reference, then timed it against SGLang's kernel on the same H200 in the same run. Each score was a <Term id="speedup">speedup</Term> (SGLang's time divided by the entry's), so `2.00×` takes half the time.

The serving track ({servingTrack}) moved to the whole system: an entry was a patch to SGLang itself, scored on an {GPUS}-GPU server answering live conversations. That board paid the prize pool, listed in the [official summary](https://openkernelchallenge.dev/llms.txt) as "$100,000 on the serving board: 1st $50,000 and a signed H200", with prizes down to tenth place. Kernel-board standings decided queue priority when shared benchmark servers were busy.

## What each problem asked

Each kernel problem timed one kind of work in a layer:

- <a href={officialUrl("muse_bf16_proj")}><code>muse_bf16_proj</code></a>: the five dense projections of a layer (`qkv_gate`, `o`, `router`, `pooler`, `unpooler`), multiplying 16-bit weights (32-bit for the router) by incoming activations. At 1 token it is memory-bound GEMV; by {count(maxProjTokens)} tokens it shifts toward compute-bound tensor-core GEMM, so one submission must handle both regimes. Chapters [4](/chip), [5](/kernel), and [8](/batching).
- <a href={officialUrl("muse_moe_w4a16")}><code>muse_moe_w4a16</code></a>: the experts stage on one GPU, unpacking 4-bit NVFP4 weights for whichever of the {LOCAL_EXPERTS} local experts were chosen and multiplying them with 16-bit activations. Every active expert is read in full however few tokens chose it, and active experts change every pass. Chapters [3](/experts) and [8](/batching).
- <a href={officialUrl("muse_attention_decode")}><code>muse_attention_decode</code></a>: attention over the FP8 KV cache and its surrounding small steps, for sliding-window and full-attention layers. No weights are read; runtime is set by cache bytes and keeping all {H200.sms} compute blocks fed across variable-length conversations. Chapters [2](/attention) and [7](/attention-kernel).
- <a href={officialUrl("muse_decode_layer")}><code>muse_decode_layer</code></a>: every step of one decode layer in order on one GPU, combining the three stages above with the ~{layerChain("sliding").length}-kernel chain of norms, gates, routing, and residual updates between them. The main new target is cutting overhead by fusing steps inside a CUDA graph. Chapter [6](/layer).
- <a href={officialUrl("muse_prefill_layer")}><code>muse_prefill_layer</code></a>: a whole layer reading prompts (hundreds to {count(PREFILL_CHUNK)} tokens at once). Here the chip is compute-bound, experts run as variable-sized grouped GEMMs, and full-layer attention scales linearly with existing context for a fixed chunk and quadratically with prompt length when reading a prompt from scratch. Chapter [9](/prefill).

## How a run is judged

### Correct first

Every timed call received fresh inputs and compared outputs against a 32-bit reference (64-bit for projections). Tolerances allowed 16-bit and 8-bit rounding while catching skipped work or wrong math. In the whole-layer brief's own words:

<ul>
	{layer.correctness.map((c) => (
		<li>{c}</li>
	))}
</ul>

The whole-layer check also validates expert routing: two experts with nearly equal scores may swap, while clear winners among a GPU's local experts must be kept, and the GPU cannot receive meaningfully fewer tokens or distinct experts than the reference. Before timing, every submission had to pass correctness tests including harder non-scored shapes, and top entries were re-verified on nearby shapes in final review.

### Timing that waits for the GPU

Timing GPU code is easy to get wrong. Because the CPU queues GPU work asynchronously and moves on, a plain CPU stopwatch around a launch measures queuing rather than execution. Accurate timing records GPU-side CUDA events or synchronizes explicitly, after warm-up runs so JIT compilation and kernel loading do not count. (In this contest, compiling counted toward a run's wall-clock limit, not its score.)

To match production serving, the judge recorded each shape as a <Term id="cudaGraph">CUDA graph</Term> and replayed entry and SGLang in turns on fresh inputs. Before every timed replay it read a buffer larger than the H200's {count(H200.l2Bytes / 2 ** 20)} MiB <Term id="l2">L2 cache</Term> so neither run started with warm data left behind by the one before.

Because GPU timings vary from run to run, the judge timed pairs (swapping which side goes first) and reported the median speedup.

A slow outlier skews its own pair's ratio, while the median ignores spikes that would pull an arithmetic mean off target. The median still wobbles slightly across runs, which is why every benchmark reports a range and small gains can be noise.

### One number per problem

A problem combines speedups across its loads with the <Term id="geomean">geometric mean</Term>: multiply the *n* speedups together and take the *n*-th root, so every load counts equally regardless of size. `muse_decode_layer`'s largest load moves about {count(workRatio)} times the work of its smallest, yet a 10% gain on either moves the score by the same amount.

## The serving track's score

The serving track scored the trade between server throughput and per-person speed. Each patched server answered live conversations with {people(servingLoads)} people at once. Each load yielded tokens/s per GPU (throughput) and tokens/s per person (interactivity), tracing each server's curve. At each load, the judge read the entry's throughput at the per-person speed unmodified SGLang achieved and divided by SGLang's throughput, comparing both servers at equal speed per user. The score was the geometric mean of those ratios, so unmodified SGLang scores `1.00`.

The rules in the [official summary](https://openkernelchallenge.dev/llms.txt) tie a patch to the chapters above: it had to be lossless (no lower precision or skipped work), keep time to first token within 2× of SGLang (Chapter 9), stay within +2 GB of SGLang's per-GPU memory (Chapter 8), and remain clean enough for SGLang's maintainers to consider accepting.
